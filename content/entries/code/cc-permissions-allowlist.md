### ❓ Что это

Режимы доступа — грубая настройка. Точная — правила `allow` / `ask` / `deny` для конкретных инструментов и команд. Управляются командой `/permissions` (алиас `/allowed-tools`) и хранятся в `settings.json`, то есть переносятся между машинами через git.

### 🎯 Зачем тебе

* **Разрешить рутину, оставить вопросы на опасном.** Чтение файлов и запуск тестов — без подтверждения; всё, что пишет в сеть или удаляет, — со спросом.
* **Явный запрет сильнее забывчивости.** `deny` на команды, которые вы точно не хотите видеть автоматическими.
* **Командная настройка.** Правила в репозитории означают, что у всех участников одинаковые границы.

### 💻 Минимальный пример

```json
{
  "permissions": {
    "allow": [
      "Read",
      "Bash(npm run test:*)",
      "Bash(git status)",
      "Bash(git diff:*)"
    ],
    "ask": [
      "Bash(git push:*)"
    ],
    "deny": [
      "Bash(rm -rf:*)",
      "Read(./.env)",
      "Read(./secrets/**)"
    ]
  }
}
```

Дополнительно ограничить доступный набор инструментов на запуск можно флагом `--tools`: `--tools ""` выключает все встроенные, `--tools "Bash,Edit,Read"` оставляет перечисленные.

### ⚠️ Грабли

* **`deny` на чтение файла — не шифрование.** Файл по-прежнему лежит на диске и доступен любому процессу с вашими правами; правило защищает от того, что его прочитает агент, а не от утечки в принципе.
* **Шаблоны обманчивы.** `Bash(git:*)` разрешает и `git push --force`, и `git reset --hard`. Разрешайте конкретные подкоманды.
* **Слишком строгие правила обходят.** Если работа постоянно упирается в подтверждения, кто-нибудь включит `bypassPermissions` — и настройка потеряет смысл.
* **Проверяйте после изменений.** `/permissions` показывает действующий набор — сверяйтесь с ним, а не с тем, что вы думаете, что настроили.
