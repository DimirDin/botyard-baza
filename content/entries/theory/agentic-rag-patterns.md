### ❓ Что это

**Agentic RAG (Агентный RAG)** — это эволюция классических систем Retrieval-Augmented Generation. Вместо линейного процесса «пользовательский запрос → поиск в базе векторов → генерация ответа», агентная архитектура дает LLM возможность самостоятельно управлять процессом поиска: выбирать источники информации, анализировать промежуточные результаты, переформулировать поисковые запросы и при необходимости запрашивать дополнительные данные через инструменты (например, веб-поиск или SQL-запросы).

### 🎯 Зачем тебе

* **Качество ответов на сложные вопросы**: Классический RAG часто пасует перед многошаговыми запросами (например, «Сравни финансовые результаты компании А и компании Б за прошлый год»). Агентный RAG разбивает эту задачу на подзапросы, находит данные по каждой компании отдельно, а затем синтезирует финальный ответ.
* **Самокоррекция**: Если первый поисковый запрос вернул пустые или нерелевантные результаты, агент поймет это и перепишет поисковый запрос (Query Reformulation).
* **Интеграция разнородных источников**: Агент может объединить поиск по векторной базе знаний (семантический поиск по документации), структурированный поиск в SQL (выборка транзакций) и веб-поиск (свежие новости).

### 💻 Минимальный пример (логика агента)

Типичный цикл работы Agentic RAG строится по схеме ReAct (Reasoning and Acting):

```
Шаг 1. Мысль: Пользователь хочет узнать актуальную стоимость акций Apple. Мне нужно найти эту информацию в сети.
Шаг 2. Действие: Вызвать инструмент web_search с параметром "AAPL stock price".
Шаг 3. Наблюдение: Результаты поиска показывают $180.50 на момент закрытия биржи.
Шаг 4. Мысль: Данные получены, они релевантны. Теперь я могу сформировать финальный ответ.
Шаг 5. Ответ: Текущая стоимость акций Apple (AAPL) составляет $180.50.
```

### ⚠️ Грабли

* **Бесконечные циклы**: Без жестких ограничений (max iterations) агент может попасть в бесконечный цикл поиска, если нужной информации нет в доступных источниках. Всегда ограничивайте максимальное число вызовов инструментов (например, не более 5-10 шагов).
* **Расход токенов**: Из-за многократных запусков модели и чтения больших объемов найденного текста в контекст, агентный RAG обходится значительно дороже обычного. Для оптимизации стоимости обязательно используйте **Prompt Caching** для системных промптов и неизменных баз знаний.
* **Смешивание контекста**: Модель может запутаться в противоречивых данных из разных источников. Задавайте четкие правила приоритета информации в системных инструкциях (например, «локальная база данных имеет приоритет над веб-поиском»).
