### ❓ Что это

У Claude API не один тип креденшела, а несколько, и они сильно разные по «радиусу поражения»
при утечке:

| Тип | Что может | Где уместен |
|---|---|---|
| Обычный API-ключ | звать модель | рантайм приложения |
| Admin API key (`sk-ant-admin...`) | управлять организацией, ключами, людьми | локально у админа, ротация |
| OAuth-профиль (`ant auth login`) | как у человека | машина разработчика |
| Сервисный аккаунт + WIF | как у нагрузки, без секрета | CI |

### 🎯 Зачем тебе

Практика «один ключ на всё, лежит в `.env`» ломается ровно в тот момент, когда `.env` уезжает
в репозиторий. Разделение по уровням превращает катастрофу в неприятность.

### 💻 Минимальный пример

Минимальный набор правил, который стоит внедрить до, а не после инцидента:

```
рантайм-приложение   → обычный ключ, только он, из секрет-менеджера
CI                   → сервисный аккаунт + WIF, секрета нет вообще
разработчик локально → ant auth login, ключ не экспортируется
админские операции   → отдельный admin-ключ, не в .env проекта
```

Проверить, что именно сейчас активно:

```bash
ant auth status
```

### ⚠️ Грабли

- **Экспортированный ключ затеняет всё остальное** — и профиль, и federation. Он первый
  в порядке разрешения. Отсюда же берётся «на CI работает не тот аккаунт».
- **Ключ в истории шелла** — `export ANTHROPIC_API_KEY=sk-...` остаётся в `.zsh_history`.
- **Ключ в публичном репозитории** сканеры находят за минуты. Если это случилось — ротация,
  а не удаление коммита: история остаётся в форках и кэшах.
- **Секрет для агента — отдельная история.** Для Managed Agents есть vault-креденшелы,
  которые подставляются на выходе и вообще не попадают в песочницу.
