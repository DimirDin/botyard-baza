### ❓ Что это

**Deployment** — объект, который запускает сессии агента автономно по cron-расписанию.
Каждое срабатывание создаёт **deployment run** — отдельную запись прогона, которую можно
посмотреть постфактум.

Это то, ради чего обычно поднимают свой планировщик: «каждую ночь собери отчёт»,
«раз в неделю проверь зависимости». Здесь планировщик не нужен — ни cron на VPS,
ни Actions по расписанию, ни воркер, который держит соединение.

### 🎯 Зачем тебе

Если задача звучит как «пусть само запускается по времени», Managed Agents с расписанием почти
всегда проще, чем собственная обвязка: нет процесса, который надо мониторить, нет состояния,
которое надо хранить, нет «а кто перезапустит, если упало».

### 💻 Минимальный пример

```python
deployment = client.beta.deployments.create(
    agent_id=AGENT_ID,
    schedule={"type": "cron", "expression": "0 3 * * *"},   # каждую ночь в 03:00
)

# история срабатываний
runs = client.beta.deployment_runs.list(deployment_id=deployment.id)
```

Жизненный цикл управляется явно: деплой можно поставить на паузу, снять с паузы и заархивировать.

### ⚠️ Грабли

- **Расписание — не гарантия ровно одного прогона.** Проектируй агента идемпотентным:
  повторный запуск на тех же данных не должен ломать результат.
- **Пауза не отменяет уже запущенную сессию** — она влияет на будущие срабатывания.
- **Стоимость набегает молча.** Ночной агент, который работает по часу, — это $0.08 runtime
  плюс токены каждую ночь, и никто не смотрит на счёт до конца месяца. Ставь бюджет сессии.
- **Ошибки некому показать.** В интерактивном сценарии падение видит человек; здесь его увидит
  только тот, кто пойдёт читать `deployment_runs`. Заведи вебхук или проверку.
