### ❓ Что это

**Vault** — хранилище секретов на стороне Anthropic. Креденшел типа `environment_variable`
кладётся в vault, а при исходящем запросе агента **подставляется на egress** — то есть значение
никогда не попадает внутрь песочницы и не видно ни агенту, ни тому, кто читает логи сессии.

Агент знает, что переменная существует, и может ей пользоваться. Прочитать её значение —
не может.

### 🎯 Зачем тебе

Классическая дилемма агента: чтобы сходить в стороннее API, нужен токен, а любой токен внутри
контейнера — это токен, который модель может выложить в ответ, записать в файл или отправить
не туда. Vault убирает саму возможность: утечь нечему, значения в контейнере нет.

Раньше единственным способом было держать креденшелы у себя и оборачивать каждый вызов
в кастомный тул на своей стороне. Это по-прежнему рабочий запасной вариант — например,
для self-hosted окружений, — но больше не единственный.

### 💻 Минимальный пример

```python
vault = client.beta.vaults.create(name="prod-integrations")

client.beta.vaults.credentials.create(
    vault_id=vault.id,
    type="environment_variable",
    name="JIRA_TOKEN",
    value="...",          # уходит в хранилище и назад не читается
)
```

Дальше агент ссылается на vault, и в его запросах `JIRA_TOKEN` подставляется на выходе.
В самом контейнере переменная пустая.

### ⚠️ Грабли

- **Vault ≠ переменная окружения контейнера.** Если код агента печатает `os.environ["JIRA_TOKEN"]`,
  он увидит пустоту — и это правильное поведение, а не поломка.
- **Подстановка работает на egress агента**, значит помогает только для исходящих вызовов.
  Для секрета, который нужен коду внутри песочницы «как значение», vault не подходит —
  но такой сценарий и есть тот самый риск утечки.
- **Self-hosted окружения** остаются на старой схеме с host-side тулами.
- **Не путай с memory stores** — это разные объекты: vault про секреты, memory store про
  переживание знаний между сессиями.
